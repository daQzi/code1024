# Task 平台额度与耐久投递

本接点使用本站 `user_platform_quotas` 和既有 Redis 额度缓存，不复制 New API 的用户账本。
迁移 286 补齐持久 JS Task 在资金提交与 Redis 更新之间的崩溃恢复。

## 一次结算包含什么

同一个 PostgreSQL 事务同时提交任务终态账单、用户解冻/扣费、Key/订阅/账号额度、普通用量日志，
以及非订阅正费用任务的平台额度和一条 `sub2api_generation_quota_outbox` 记录。任一项失败整笔回滚。
零费用、确认失败退款、订阅来源及没有有效限额的用户不创建正额度事件，也不重建已删除限额。

额度行在分配事件序号前锁定，因此同一额度身份的事件保持顺序。事件仅保存任务 ID、额度行 ID、
用户/平台、实际 USD 金额、窗口和投递租约，不保存请求正文或密钥。重放结算不重复创建事件。

## PostgreSQL 与 Redis 如何去重

- 数据库额度和 Redis 快照都带 `generation_cursor`，表示绝对用量中已经包含哪些 Task 事件。
  回源必须在同一条查询中读取用量和 cursor，不能先读旧用量、再配上新 cursor。
- 固定一个后台 worker，每秒最多取 32 条；每步三秒上限。多个实例通过数据库租约和同额度头部顺序协调，
  不在等待 Redis 时持有 SQL 事务。失败十五秒后重试，过期租约可重领。
- Redis Lua 原子地累加金额并推进 cursor。重复投递和“Redis 成功、SQL 尚未确认就崩溃”不会再次累加。
  cursor 用十进制字符串比较，超过 JavaScript/Lua 浮点安全整数仍保持准确。
- 缓存不存在时无需补造 Hash：下一次准入直接从数据库读取已包含金额的用量/cursor；之后旧事件会被跳过。
  旧版 v1 Hash 可在首次事件时补上身份/cursor，保留其中的普通调用用量。
- 新缓存使用额度行 ID 区分删除后重建的限额。旧任务事件和携带旧身份的快照不能记入新限额。
  晚到的数据库回填也不能覆盖已经包含更新 Task cursor 的 Redis 结果。

`user_platform_quota_flusher_enabled` 开关的两种模式均走这条 Task 事务。开启绝对快照 flusher 时，
每批先按顺序锁住额度行，再在新语句快照中合并 Redis cursor 之后的 Task 事件，防止旧 Redis 快照
把数据库已提交的任务费用覆盖掉；包含过的事件不重复加入。批次仍最多 6000 行，每行十个参数。
手工重置写入同窗口标记，已读取的旧窗口快照不能恢复重置前费用；其他窗口保留。

## 范围与升级

这是持久 JS Task 的耐久额度投递，不把普通同步文本请求或旧原生视频观察记录改造成新的财务 outbox。
旧 Hash 没有额度行身份时仍保留既有兼容语义，回源或首次事件后补齐；不为升级前已结算的任务补造事件。
上游没有真实最终费用或还在人工对账的任务，不会为了额度更新而猜测金额。

额度准入仍沿用本站的事前检查、完成后累加语义；并发在途请求可能超出限额，不能把此功能描述成
平台限额的全局原子预留。Redis 故障期间数据库额度已提交，普通网关沿用已有数据库回源策略；
恢复后的投递逐步补齐缓存。投递记录保留为 Task 财务审计和旧快照合并依据，不可单独清空或提前裁剪。

升级先运行正式迁移，再使用新版本处理 Task 与 flusher。回退到忽略 cursor 的旧二进制前，必须先停止
新任务并停用旧式快照 flusher、排空投递并核对额度；仅数据库健康检查不等于回退验收。生产升级与回退
演练仍列 R8，本地隔离 PostgreSQL/Redis 模拟不能代替生产验收。
