# 统一插件系统迁移：开发计划与任务清单

> **架构修订（2026-11-22）**：按用户最新补充，改为[独立 New API 插件与任务引擎](NEWAPI_ENGINE_DECOUPLING.md)，Sub 原生插件保持独立、不再整合运行时/生命周期。本文保留上一版 50 项清单；涉及“双运行时统一控制层”、原生 SDK 重建、强制接管旧任务等描述不再执行，P0～P9 的修订见新方案第 7 节。任务状态机、调度和查询由新引擎拥有，主站负责适配账号、事务资金和公共页面。

更新日期：2026-11-22。状态：**计划已整理，以下待办尚未因此完成；本轮不新增功能、不操作生产。**

## 1. 先说结论

继续使用当前 Sub2API 作为主站，把现有实现收拢成一套可以独立开发的插件模块。**一个插件中心，两种运行时，一套账号、任务、账本和监控。**

可以把它理解为：主站是一家店；New API JS 插件和 Sub 原生插件是两种规格的插头。统一插座负责识别规格、权限和版本；店里的账号、钱和订单仍由主站管理。不能只把两种插件摆在同一页面，就认为已经兼容。

当前已经有插件中心、市场、后台任务、日志和模型广场，不需要推倒重建。真正剩下的是：补齐 New API 宿主行为、把两种插件纳入同一管理和执行规则、完成模块解耦，并给开发者可验证的规范。

本计划共 **10 个阶段、50 个工作项**，包含增量开发、现有能力回归、文档和交付。它们不是 50 个等量的小改动，也不据此估算完成百分比或承诺工期。官转二、官转五等渠道专项另列后续批次。

## 2. 范围与对照依据

### 2.1 已确认的范围

1. New API 原版 JS：以固定基线为对象，**不修改插件源码即可导入、安装并执行其声明的、通过验收的功能**；不要求加入本站私有必填字段。
2. Sub 原生 `.s2plugin`：保留包格式、签名、gRPC 与 UI Bridge，通过适配层进入统一系统；不强迫全部重写为 JS。
3. 重叠的插件契约、配置和执行语义，以 New API 为主；Sub 独有的传输、权限、持久任务和财务能力作为补充。
4. 整个插件模块可独立构建、测试和版本管理。先同仓拆包，主站通过接口集成；本轮不拆成额外微服务。
5. 新建上游仍在“账号”中进行。插件中心负责安装、来源、版本、能力和发布，不再建一套上游账号。
6. 任务日志使用独立菜单；模型广场按当前分组展示，点击进入可直达的独立页面。
7. 通用系统和开发规范优先完成；官转二、官转五、其他新渠道以后按规范作为社区插件开发和联调。
8. 保留已有插件、账号绑定、固定版本、接口与历史记录。对在途任务，不换驱动、不重发生成、不套用新价格。

### 2.3 “一样”的验收口径

- **契约兼容**：同一原版源码的 metadata、hooks、类型、默认值和错误语义可被正确识别。
- **宿主兼容**：声明的路由、凭据、文件、转换、状态和费用能在真实主站链路执行；不是只在 JS 沙箱里调用成功。
- **产品对齐**：安装、账号绑定、市场、日志、价格和监控可完成相同业务流程；页面按本站 Vue 风格实现。
- **扩展兼容**：Sub 原生传输与本站独有能力继续可用，扩展与 New API 标准字段分开，不能改变原版源码要求。

完成后应发布“针对哪个固定基线、哪些能力验收通过”的报告。New API 的 Go 内置渠道、未来插件和未来契约版本不自动包含在该承诺中。

### 2.4 本轮迁移的边界

迁移插件契约和对应业务能力，不整体替换主站的登录、用户、支付和所有静态渠道；也不把现有普通批量图片等产品业务全部重写成 Task。基线已经支持的图片/Responses Task 仍必须实现，不能用这个边界删掉兼容范围。额外微服务、独立市场网站和不属于固定基线的新协议，需要单列需求，避免通用系统迟迟不能交付。

兼容方向是“两类插件都能进入当前 Sub 站点”。独立模块为其他宿主适配保留接口；若以后要在原版 New API 站点中执行 `.s2plugin`，还需要为那边实现相应宿主适配，不能把这个结果算作本次双格式导入已经自动获得的能力。

## 4. 目标结构：怎么拆，怎样统一

### 4.1 建议的包边界

以下是目标目录，**尚未创建**；最终 Go module/import path 在 P1-01 随仓库发布身份固定。

```text
sub2api/
├── plugin-kit/                       # 新增独立 Go module，可 GOWORK=off 单独测试
│   ├── contract/                     # 固定 New API 契约、类型/schema、兼容性描述
│   ├── runtime/                      # JS 与 native 统一 Driver 接口及各自执行器
│   ├── controlplane/                 # 注册、版本、市场和生命周期的通用编排
│   ├── policy/                       # 能力、版本、权限和执行计划判定
│   ├── billing/                      # 纯表达式求值与快照类型，不存用户余额
│   ├── ports/                        # 存储、事务、凭据、文件、出站、事件等宿主接口
│   ├── testkit/                      # 固定原版脚本、模拟上游、双运行时契约测试
│   └── cmd/pluginctl/                # 独立校验、模拟执行、兼容报告
├── backend/internal/pluginhost/      # 新增 Sub 宿主适配，沿用现有 service/repository
├── backend/internal/service/         # 账号、调度、账本、任务事实等仍由本站拥有
├── backend/pkg/pluginapi/            # 旧公开 import/proto 的兼容入口，避免破坏已发布插件
└── frontend/packages/plugin-ui/      # 可独立检查/构建的 Vue 管理组件及 client 类型
```

不是只搬 `internal/newapi` 目录：通用注册、生命周期和管理编排也要通过 ports 脱离宿主具体 service；宿主保留的代码只负责把本站账号、数据库、权限、任务和账本接上。

前端先拆独立 Vue 包，通过 client、权限、通知、路由跳转和文案注入集成。保留现有样式，不为了“像 New API”引入 React。

### 4.2 宿主接口与所有权

| 接口/职责 | 插件模块负责 | Sub 宿主负责 |
| --- | --- | --- |
| Registry / PackageStore | 格式识别、版本/摘要、状态机、来源和安装编排 | 持久化、审计、管理员权限和文件存储 |
| Account / Credential | 声明所需字段、登录步骤、固定连接和凭据身份 | 账号归属、密文、代理、授权、续期租约与停用策略 |
| Outbound / Media | 生成请求描述符、声明允许主机和文件需求 | 真实 HTTP/WS/I/O、SSRF 限制、超时、内存/文件预算 |
| Task / Artifact | 协议解码、提交/查询/结果归一化、产物描述 | 持久任务、幂等、租约、私有制品、对账和历史查询 |
| Pricing / UnitOfWork | 表达式计算、单位、价格与用量快照契约 | 同事务准入/冻结/结算/退款、资金流水、额度 outbox |
| Metrics / Audit | 产生有界、脱敏的执行和终态事件 | 唯一落库入口、聚合、权限、模型广场通知 |

核心模块不能导入本站 `internal/service`、`internal/repository`、Gin handler 或数据库实现。持久化和事务使用调用方实现的 ports；不得在模块内增加第二套用户余额或第二个任务事实库。

特别处理当前媒体包对 `internal/pkg/httputil` 的依赖：通过预算接口注入**同一份请求/进程预算**，不能复制一套计数器后让同一请求绕过总限制。

### 4.3 冲突与组合规则

1. 插件身份包含运行时、来源、原 key、版本和摘要；展示名相同不等于同一作品。原版 JS 的 key/version/原始字节不改写，避免影响其内部行为。
2. 同一入口存在重复实现时，显式确定执行计划；已支持的重叠协议优先选择 New API 驱动。原生 OAuth 传输等补充能力通过明确适配点组合。
3. 一次调用只能有一个负责发出付费生成的主执行器。允许按阶段组合 Transform、协议适配和传输，但不能两个驱动各提交一次。
4. 跨运行时回退只允许发生在**确定尚未发送**的阶段；发送结果未知时进入对账，禁止自动换运行时/账号再发一次。
5. 不支持的 route/hook/capability 在选择和准入时清楚报告；必要能力不满足就拒绝，不静默跳过再标记成功。
6. 禁用影响新请求；旧任务按创建时快照继续查询/交付。卸载前检查账号、实例、父任务、在途任务和版本引用；禁止强删仍需执行的源码或二进制。
7. 普通作者继续使用社区命名空间。管理员导入原版与作者发布新作品分开，不能用“原版兼容”取消防抢注/防覆盖约束。
8. JS 的 user/token/group/channel 上下文只映射当前获授权的本站身份和明确的渠道类型；未知映射不猜。不得直接序列化整条账号/Key 记录，也不能为兼容字段额外开放全账号目录。

## 5. 三个关键移植：钱、任务日志、监控

### 5.1 计费：移计算规则，复用本站的钱包

参考 New API 的 `pkg/billingexpr/`、`service/task_billing.go` 和任务快照，迁移表达式语义、用量归一化、单位、预估与最终求值；沿用本站现有账户、余额、Key/分组规则与资金流水。

- **完整计算**：覆盖 Task `u()`/profiles、token/cache/image/audio、`param/header`、时间规则、分档和规则 trace；保留不同协议对 token 的归一化语义。`fixed()` 的适用范围和校验按基线实现，不能当作 Task USD 标量直接套用。
- **固定依据**：创建时保存所选表达式/版本/摘要、公开与上游模型、分组规则、单位和换算、预估事实、成本来源/有效期；完成时依据原快照叠加实际事实，不按最新价格回算历史任务。
- **分清单位**：Task 表达式输出 USD；token 表达式以美元/百万 token 的尺度求值，再换算到本站金额。不能复制 New API 的 quota 整数直接作为本站金额。
- **一笔事务**：任务受理/冻结、终态/结算/退款、资金流水与已有 Task 额度 outbox 通过明确的事务接口原子写入；不能由两个独立 Save/Debit 调用假装原子完成。
- **异常可查**：已确认失败退款；未知提交、缺最终事实、求值失败分别保存原因。本站已有人工对账和冻结上限继续保留；与基线的异常处理差异在报告中明示，不宣称完全相同。
- **普通同步调用**：已有单次计费接点继续使用。若本批新增媒体/工具/表达式要求扩大预留，必须在真实发送前证明同一账本内原子准入；不能把 Task outbox 的完成当成全站同步预留已完成。

价格管理区分四件事：上游报告的**用量**、可追溯的**成本单价/账单**、管理员配置的**本站售价**、最终确认的**差额/利润**。New API 插件的 usageSchema 或余额接口不天然等于报价接口。仅有文档或数量时不猜成本；没有自动报价的上游仍支持手工成本和固定售价。自动更新成本不自动覆盖管理员售价，在途任务不改价。

### 5.2 任务日志：迁移行为，复用任务事实

参考 New API `model/task.go`、`controller/task.go`、`service/task_plugin_view.go`、`service/task_plugin_audit.go` 与 task-logs 页面，扩展本站现有“任务日志”，不再创建一份并行的日志任务表。

- 保留现有**执行、交付、计费**三种状态，增加与 New API NOT_START/SUBMITTED/QUEUED/IN_PROGRESS/FAILURE/SUCCESS/UNKNOWN 的明确映射；未知不能显示成失败或成功。
- 通用详情由任务类型、协议、动作、公开输入摘要和产物列表组成；消除 `GenerationVideoFields`/默认 `video` 产物对图片、文本或其他任务的限制。
- 列表可按任务 ID、模型、插件、状态、账号/分组、时间、计费状态筛选；详情展示事件时间线、版本/摘要、费用依据、产物与允许的动作。用户只能看自己的任务；账号、上游 ID 和内部字段按现有权限脱敏。
- 原始 state、凭据身份、上游任务 ID、内部价格/连接快照和敏感参数属于私有数据，不能随 New API 的 private_data 一起原样暴露给前端。
- 视频 ID、文件绑定、事件、外键和索引一起审计；现有迁移中存在 `VARCHAR(46)` 约束，通用任务设计不能只修改一个 Go ID 类型。旧 URL/ID 和在途任务必须继续可查。

### 5.3 监控：统一采样，按真实证据展示

参考 New API `pkg/perf_metrics/`、`middleware/performance.go`、`controller/performance.go` 和模型性能页面；复用本站已有 recorder、数据库防重、模型/分组聚合和失效通知。

- HTTP 200、WS 握手或提交拿到任务 ID 不代表模型完成成功。同步调用在真实结束时采样；Task 在最终状态采样一次；WS/Realtime 按独立轮次采样。
- 默认展示状态段、成功率和平均耗时；文本存在有效证据才展示 TTFT/吞吐。视频默认展示任务完成耗时；若确有有效 token 与生成时钟，可按同一规则算 TPS，不能按时长编造 token。
- TPS 使用总输出 token ÷ 总有效生成时间，不能平均每次请求的 TPS。排队、上游生成、最终交付分别计时；样本窗口、取消/排除类别和分母与基线对照固定。
- 按模型与分组隔离；内部可按插件/运行时排查，限制标签基数。普通用户不因此看到其他分组、账号或单条内部请求。
- 这是秒级持续刷新，不承诺零延迟。现有写库/通知具有批处理与检查间隔，断线走普通刷新回退；同时保留 accepted/persisted/dropped 计数，避免丢样被误认为零失败。
- 遥测、界面通知和 Transform report 均不能代替财务 outbox；监控失败不回滚已经完成的账务，也不触发再次付费生成。

## 6. 分阶段开发任务

### 6.1 如何读任务表

- 所有任务当前均为**待执行/待验收**，不是把现有部分实现归零；“增量”表示沿用现有代码补缺口，“重构”表示迁移结构并证明行为保持，“验收”表示不预设需要新增功能。
- 优先级“阻断”先完成；“必需”属于最终系统交付范围；“交付”负责证明可用和上线。它们不等于额外的三个阶段。
- 任务依赖是最小约束。建议按 P0 → P1 → P2 开始；完成接口和身份规则后，Provider、Task、文件和定价逐条推进；最后完成统一页面、规范和验收。
- 表中目录均相对仓库根目录；含 `plugin-kit/`、`pluginhost/` 和 `frontend/packages/` 的目录是拟新增落点。具体文件拆分遵循现有项目风格，不先为每个接口建立复杂框架。

模型可见范围至少取以下交集：**当前用户能访问的账号/分组配置模型 ∩ 分组许可 ∩ 实际可执行的宿主/插件能力**。插件声明和模型发现提供候选；全局模型库提供名称/介绍；都不能单独扩张支持集合。未定价状态只针对本就处于该集合内的模型展示，不能借此把全量模型加回来。

## 8. 分批提交和阶段出口

每批都遵循“先接口与用例 → 迁移一个真实调用点 → 补齐同类路径 → 验证 → 本地提交”。不把所有目录移动和所有新功能塞在一个提交里；也不按文件机械拆成几十个难以回退的微提交。

| 建议提交组 | 对应任务 | 该组可审查的结果 |
| --- | --- | --- |
| C00 计划与范围 | 本文及历史文档入口 | 只改文档，明确现状与待办；即本轮产出 |
| C01 基线与矩阵 | P0 | 固定来源、逐项契约和历史保护用例 |
| C02 模块接口与 JS 提取 | P1-01、P1-02 | 独立模块可运行，先证明一条旧链路行为一致 |
| C03 native/控制层/UI/构建 | P1-03～P1-05 | 双运行时与管理模块独立，主站、Docker 和 CI 都能构建 |
| C04 统一导入与市场 | P2 | 两格式同入口、固定字节/版本和明确能力报告 |

**阶段出口：**

- **M1：可独立开发**。P0～P2 完成，两种格式均能走统一控制层和独立模块；这时不宣称完整宿主兼容。
- **M2：协议能力齐全**。P3～P5 完成，固定基线的可执行 route/hook/file/WS 都有宿主用例；费用和产品验收仍看 M3。
- **M3：业务闭环齐全**。P6～P7 完成，新增能力进入同一账本/任务/日志/模型分组/指标链。
- **M4：系统可交付**。P8～P9 完成，文档、示例、逐项验收、升级与回退证据齐备。真实厂商的未测项独立列明。

任一阶段发现基线新增依赖或行为差异，回写同一任务 ID 和兼容矩阵，不能在聊天里另开一份不受控的“已完成”口径。每次交接写清：改动、测试命令与结果、未测项、本地提交、是否已推送、是否已发布和是否已部署。

## 9. 验收、升级和回退如何落地

### 9.1 每批验证

1. 结构重构：相关独立模块 `GOWORK=off go test ./...`、`go build ./...`，再验证宿主真实入口；前端包和主站分别类型检查/构建。
2. 资金/任务：真实隔离 PostgreSQL，覆盖并发、租约、重复终态、事务中断、重启、退款、对账与已有 quota outbox。不得只有 mock 就认定原子性正确。
3. 流/文件/WS：模拟实际 HTTP/WS/I/O，验证最终客户端内容、终态、取消和资源回收；不是只测试转换函数返回了一个对象。
4. UI：在有数据和空数据下验证安装、账号绑定、分组切换、任务详情、价格和监控；重大流程同时检查普通用户与管理员权限。
5. 文档批次：检查链接、任务 ID/依赖、状态和来源的一致性、`git diff --check`；只改文档不重复运行无关的整套 Go/前端测试。

CI 明确区分“核心模块通过”“宿主集成通过”“真实厂商通过”。精确测试数量以当次报告为准；不沿用上一轮数量给新改动背书。

### 9.2 数据和版本切换

- **先扩展再切流**：新增可兼容字段/表约束和读取逻辑，保留旧路径；新驱动通过显式配置先用于新请求。
- **固定历史**：旧插件源码/二进制、价格、连接和登录身份不被升级覆盖。旧任务缺少的证据不补造，不把旧未知任务自动重发。
- **worker 能力隔离**：混合版本期间，worker 必须按能理解的任务/驱动版本认领；做不到时采用有控制的停新任务/排空/升级流程，不能让旧进程误执行新任务。
- **回退先停新流量**：关新驱动准入，保留读取和原版本查询/结算能力；有新版在途任务时，保留能处理它们的 worker，或按演练步骤暂停处置。
- **资金事实不倒退**：不能拿升级前数据库备份覆盖仍有新资金流水的生产库。备份用于灾难恢复演练；普通应用回退使用兼容 schema 和已记录的资金事实。
- **先验后删**：兼容 facade、旧列和旧驱动等独立后续版本再清理，前提是引用和在途任务已清零，有实际检查记录。

### 9.3 发布前必须回答的问题

- 固定基线中的每个可执行能力，是否都有源码依据、宿主入口和通过的用例？有没有未测分支被写成“完整兼容”？
- 原版 JS 的 key、version、源码字节和摘要是否保持？原生签名、proto/UI Bridge 和 HostService 边界是否保持？
- 原有账号/接口/任务/余额是否保留？未知提交是否仍不会重复发出？新功能是否可能绕过发送前价格/额度准入？
- 模型列表、价格、例子和性能是否都属于同一当前分组？无样本、指标丢样和未定价是否如实展示？
- 独立包能否离开主站构建测试？Docker/Release 是否包含它？旧 worker 和回退是否演练？
- 实测通过、仅模拟通过、未测厂商、许可/来源说明和部署状态是否分开记录？

## 10. 系统完成后的社区插件批次

官转二、官转五、火山和其他新增上游，系统完成后按 P8 文档独立开发/整理，不再通过渠道专项反向扩张宿主私有接口。

| 后续工作 | 处理方式 | 验收 |
| --- | --- | --- |
| 官转二/官转五已有实现 | 保留现有 key/版本/账号/在途任务，按新 SDK 整理为社区发布物；是否使用新 key 另做显式迁移方案 | 安装新版本不改变旧任务；真实最小额度调用/文件/最终用量/账单和产物链完整 |
| 官转五持久上传扩展 | 现有专用实现和加密检查点继续保留；先判断能否由通用文件 ports 表达，再逐步去除渠道耦合 | 不损失上传恢复、失败 abort 和付费提交边界；不能为“纯脚本化”回退已有耐久性 |
| 火山等原版/新插件 | 原版能直接用则不修改源码；新增能力按公开契约和 mock 示例开发 | 连接映射、模型/profile、文件、价格、幂等和终态用量均有证据 |
| 社区市场上架 | 作者提交、源码/包、文档、版本与宿主最低能力、审核和摘要/签名 | 可从市场安装到账号并定位任务/费用/监控；不会获得未申请权限 |

后续真实验收需要：可用测试账号/连接、允许的模型与明确额度、可使用的测试素材、可追溯价格/账单依据；登录回调或邮件能力按所测插件补充。这些资料通过站内安全配置提供，不写入源码、fixtures 或提交。**现在不需要先提供这些资料，通用系统还有可独立推进的开发。**
